01 The gap kiri fills AWS devs got one local endpoint for everything years ago. GCP devs never did.
Option A — real GCP

Slow, costly, online-only

Every test run needs credentials and a network round-trip, spends real money, pollutes shared projects, and can't run in an air-gapped pipeline.

Option B — official emulators

Five binaries, five services

Google ships emulators for Pub/Sub, Firestore, Bigtable, Datastore, and Spanner — separate processes, separate flags, and no way to see cost.

kiri

One process. One endpoint. The whole platform — priced.

Point any Google Cloud client library at localhost. 108 services answer locally, share state across REST and gRPC, persist to disk, and carry a real pricing catalog so you can predict what your design costs.

02 Quickstart Running and talking to your first service in under a minute.
01

Start the emulator

Build the image from source and run it. REST on 4443, gRPC on 8085.

# one binary, two ports
docker build -t kiri -f docker/Dockerfile .
docker run -p 4443:4443 -p 8085:8085 kiri
02

Point your SDK at it

Nothing in your app changes but the endpoint. Storage and Pub/Sub honor their standard emulator variables.

export STORAGE_EMULATOR_HOST=http://localhost:4443
export PUBSUB_EMULATOR_HOST=localhost:8085
03

Use the real client library

The unmodified cloud.google.com/go libraries work as-is — this is the actual code your app already runs.

client, _ := storage.NewClient(ctx,
    option.WithEndpoint("http://localhost:4443/storage/v1/"),
    option.WithoutAuthentication(),
)
// bucket.Create, obj.NewWriter, sub.Receive … all local
